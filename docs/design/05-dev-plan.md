## 2. 工期：AI 辅助编程下重估

### 2.1 先修正本文档自己的一处算术错误

**原文标题写「基线 9.5 周」，但下方表格逐项相加是 10.5 周**
（1.0+1.0+1.5+1.0+1.5+1.5+1.0+1.0+0.5+0.5 = **10.5**）。

这是我上一轮撰写时的错误。**P1「不压缩」决策即基于该错误数字**，故此处先纠正基线，再重新评估。

### 2.2 AI 编程压缩的是「敲代码」，不是「验证」

把每阶段的成本拆成三类，压缩比完全不同：

| 成本类型 | 内容 | AI 压缩比 | 原因 |
|---|---|---|---|
| **C 编码** | controller / service / DTO / Prisma schema / 组件 | **5–8×** | 模式化、有明确规格、可复制 |
| **V 验证** | 不变量测试、对抗性复核、真机调试 | **≈1.3×** | 必须由人判断"断言是否断言了正确的事" |
| **N 非代码** | 90 条模板内容、法务文本、认证/备案等待 | **≈1.1×** | 需领域判断；等待是日历门，非工作量 |

**本项目的瓶颈在 V，不在 C** —— 账本正确性与权限正确性无法靠"生成得快"解决。
因此总工期降幅远小于"代码产量"的增幅。

### 2.4 为什么不是 2 周 —— 本项目自己就是反例

- **D12**：测试器退出码在第 11 项后即被锁死为 `0`，其后的 6 个检查 + 两个尾块可静默失败 → **CI 永久假绿**
- **D13**：断言把缺陷**写成正确行为**，让"绿"失去意义

这两条正是「**代码生成得快、审查没跟上**」的产物。而且 AI 让该风险**变大**：
单位时间进入主干的可疑代码更多，审查容量却不变。**生成速度提升 ≠ 交付速度提升**，
中间隔着验证这道闸门。

**本会话的直接证据**：修复 10 个缺陷、跨双端、含回归用例，耗时约 1–2 小时
（人工当量 3–5 天）；但**发现**这 10 个缺陷靠的是逐行读码 + 花括号深度检查，
**不是靠生成**。而我在本会话自身也引入了 2 个错误
（`kDebugMode` 非 const 表达式、shell `&` 优先级导致目录竞争），**全靠验证当场抓出**。

## 4. 为什么必须"一次把 schema 改到位"

**核心洞察：以下四件事是同一次 schema 变更，必须同批落地，不能分散**：

```
PointRuleVersion（版本化）  ─┐
不可变 PointRecord（含 balanceAfter）─┤
软删除 status/deletedAt      ─┼─→ 同一批 DDL + 同一批迁移
AuditLog（审计）            ─┘
```

理由：
1. 它们**互相引用**（`PointRecord.ruleVersion` → `PointRuleVersion`；`AuditLog` 记录两者的 before/after）
2. 分批会导致**中间态数据无法迁移**（例如先上 `PointRecord` 但没有 `PointRuleVersion`，
   那么这段时间的历史记录永远缺 `ruleVersion`，`03` 的 I3 不变量永久破缺）
3. 软删除的全局过滤器（Prisma `$extends`）必须与 `status` 字段**同时**上线，
   否则上线瞬间所有列表会包含已删除项

因此 **W0 必须产出完整 schema，W2 一次性实现**。
